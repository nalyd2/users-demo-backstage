# ADR-003: Event-Driven User State Synchronization

- **Status:** Accepted
- **Date:** 2026-07-26
- **Deciders:** Platform Architecture Team
- **Technical Story:** Integration of user activity state with Auth Service for real-time consistency

## Context

The application manages user accounts whose state (active, suspended, deleted) originates in the external Auth Service. Changes to this state -- account suspension, reactivation, deletion, or credential expiry -- are authoritative events emitted by the Auth Service. The current design processes user state only at login time, which introduces a window where state derived from a stale cached value can diverge from the Auth Service truth.

Key drivers for this decision:

- User state must reflect the Auth Service's view within a bounded time window (target: < 30 seconds).
- The Auth Service publishes lifecycle events (UserCreated, UserSuspended, UserReactivated, UserDeleted, CredentialExpired) through a message bus; polling the Auth Service API for changes is discouraged by its operator.
- Direct API calls to the Auth Service on every user interaction would create unacceptable latency and coupling.
- A shared database with the Auth Service is not feasible due to security boundaries and service ownership.

## Decision

We will adopt an **event-driven architecture** to synchronize user state. The application will consume Auth Service lifecycle events via an Azure Service Bus topic subscription and update its local user projections accordingly.

### Architectural Details

1. **Event Source:** Auth Service publishes domain events to a Service Bus topic `auth-user-lifecycle`.
2. **Subscription:** A dedicated subscription `user-sync-sub` receives events for this application.
3. **Consumer Service:** A background `UserStateSyncService` runs as a standalone microservice (or a background worker within the existing API host) and processes incoming events.
4. **Projection Update:** On each event, the consumer reads the current user state from the Auth Service API (to get the authoritative snapshot) and writes it to the local `users` table. This ensures the projection contains only the fields relevant to this application.
5. **Idempotency Key:** Every event carries a unique `eventId`. The consumer tracks processed `eventId`s in a dedicated `event_log` table to guarantee at-most-once processing in case of duplicate delivery.
6. **Retry & Dead-Letter:** Processing failures are retried with exponential backoff (max 3 attempts). Events that exhaust retries land in a dead-letter queue for manual investigation.

### Event Flow

```
Auth Service
     |
     | (publishes)
     v
Service Bus Topic [auth-user-lifecycle]
     |
     | (subscription)
     v
UserStateSyncService
     |
     | (deduplicate, enrich via Auth API, write)
     v
Local users table
```

## Alternatives Considered

### Direct API Calls (Synchronous Lookup)

Call the Auth Service API on every request that needs user state.

- **Pros:** Always reads the latest data; simple to implement.
- **Cons:** Adds 10-50 ms latency to every request; couples availability of this application to the Auth Service; increases Auth Service load; no offline resilience.

### Polling

Run a scheduled job that periodically queries the Auth Service for changed users using a "last modified since" pattern.

- **Pros:** No message infrastructure required; familiar batch pattern.
- **Cons:** Fixed polling interval creates unavoidable staleness; wasteful when few changes occur; Auth Service does not provide a bulk change-detection endpoint; race conditions on rapid state changes.

### Shared Database

Both the Auth Service and this application write to and read from the same `users` table.

- **Pros:** Single source of truth; no sync logic needed.
- **Cons:** Violates service ownership boundaries; schema changes require coordinated deployments; Auth Service team explicitly prohibits direct database access from external services; introduces a single point of failure.

## Consequences

### Positive

- **Decoupling:** The application does not depend on Auth Service availability for every user interaction. Stale state is tolerated until the event arrives.
- **Scalability:** Event processing can be scaled independently of request-handling capacity.
- **Auditability:** The `event_log` table provides a complete, ordered record of every state change consumed from the Auth Service.

### Negative

- **Eventual Consistency:** There is a measurable delay (sub-second to a few seconds) between an event being published and the local projection being updated. Read-after-write consistency is not guaranteed across service boundaries.
- **Infrastructure Complexity:** Requires management of a Service Bus namespace, topic, subscription, and dead-letter queue, plus the consumer host lifecycle.
- **Operational Overhead:** Dead-letter queue monitoring and replay procedures must be defined. Event schema changes require coordinated rollout across publisher and consumer.

### Mitigations

- **Idempotency:** The `eventId` deduplication guard guarantees that duplicate events do not corrupt state.
- **Health Check:** `UserStateSyncService` exposes a liveness endpoint that reports the lag between the last processed event and the current time. Monitoring alerts on lag > 60 seconds.
- **Backfill Process:** A one-time batch script reconciles the full local user set against the Auth Service on deployment, then switches to event-driven mode.
- **Graceful Degradation:** If the event consumer falls behind or is unavailable, the application continues serving requests using the locally stored state, accepting that state may be stale.

## Compliance

This ADR aligns with the following organizational standards:

- **SEP-001 Service Boundaries** -- event-driven integration avoids shared databases and direct service-to-service API coupling.
- **SEP-007 Asynchronous Communication** -- all cross-service state synchronization uses brokered messaging.
- **SEP-012 Idempotency Requirements** -- event consumers must handle duplicate delivery safely.
