# ADR-003: Sincronización de Estado de Usuario Basada en Eventos

- **Estado:** Aceptado
- **Fecha:** 2026-07-26
- **Decisores:** Equipo de Arquitectura de Plataforma
- **Historia Técnica:** Integración del estado de actividad del usuario con el Auth Service para consistencia en tiempo real

## Contexto

La aplicación gestiona cuentas de usuario cuyo estado (activo, suspendido, eliminado) se origina en el Auth Service externo. Los cambios en este estado -- suspensión de cuenta, reactivación, eliminación o expiración de credenciales -- son eventos autoritativos emitidos por el Auth Service. El diseño actual procesa el estado del usuario solo al momento de inicio de sesión, lo que introduce una ventana donde el estado derivado de un valor en caché desactualizado puede divergir de la verdad del Auth Service.

Los impulsores clave para esta decisión:

- El estado del usuario debe reflejar la vista del Auth Service dentro de una ventana de tiempo acotada (objetivo: < 30 segundos).
- El Auth Service publica eventos del ciclo de vida (UserCreated, UserSuspended, UserReactivated, UserDeleted, CredentialExpired) a través de un bus de mensajes; su operador desaconseja consultar la API del Auth Service para detectar cambios.
- Las llamadas directas a la API del Auth Service en cada interacción de usuario crearían latencia y acoplamiento inaceptables.
- Una base de datos compartida con el Auth Service no es factible debido a los límites de seguridad y la propiedad del servicio.

## Decisión

Adoptaremos una **arquitectura basada en eventos** para sincronizar el estado del usuario. La aplicación consumirá eventos del ciclo de vida del Auth Service a través de una suscripción a un tema de Azure Service Bus y actualizará sus proyecciones de usuario locales en consecuencia.

### Detalles Arquitectónicos

1. **Fuente de Eventos:** El Auth Service publica eventos de dominio a un tema de Service Bus `auth-user-lifecycle`.
2. **Suscripción:** Una suscripción dedicada `user-sync-sub` recibe eventos para esta aplicación.
3. **Servicio Consumidor:** Un `UserStateSyncService` en segundo plano se ejecuta como un microservicio independiente (o un trabajador en segundo plano dentro del host de API existente) y procesa los eventos entrantes.
4. **Actualización de Proyección:** En cada evento, el consumidor lee el estado actual del usuario desde la API del Auth Service (para obtener la instantánea autoritativa) y lo escribe en la tabla `users` local. Esto asegura que la proyección contenga solo los campos relevantes para esta aplicación.
5. **Clave de Idempotencia:** Cada evento lleva un `eventId` único. El consumidor rastrea los `eventId` procesados en una tabla `event_log` dedicada para garantizar procesamiento como-máximo-una-vez en caso de entrega duplicada.
6. **Reintento y Mensajes No Procesables:** Los fallos de procesamiento se reintentan con retroceso exponencial (máximo 3 intentos). Los eventos que agotan los reintentos van a una cola de mensajes no procesables para investigación manual.

### Flujo de Eventos

```
Auth Service
     |
     | (publica)
     v
Service Bus Topic [auth-user-lifecycle]
     |
     | (suscripción)
     v
UserStateSyncService
     |
     | (deduplicar, enriquecer via Auth API, escribir)
     v
Tabla users local
```

## Alternativas Consideradas

### Llamadas Directas a la API (Consulta Síncrona)

Llamar a la API del Auth Service en cada solicitud que necesite estado del usuario.

- **Pros:** Siempre lee los datos más recientes; simple de implementar.
- **Contras:** Añade 10-50 ms de latencia a cada solicitud; acopla la disponibilidad de esta aplicación al Auth Service; aumenta la carga del Auth Service; no tiene resiliencia fuera de línea.

### Sondeo (Polling)

Ejecutar un trabajo programado que consulte periódicamente al Auth Service en busca de usuarios cambiados usando un patrón de "última modificación desde".

- **Pros:** No requiere infraestructura de mensajería; patrón por lotes familiar.
- **Contras:** El intervalo de sondeo fijo crea obsolescencia inevitable; ineficiente cuando ocurren pocos cambios; el Auth Service no proporciona un endpoint de detección de cambios masivos; condiciones de carrera en cambios de estado rápidos.

### Base de Datos Compartida

Tanto el Auth Service como esta aplicación escriben y leen de la misma tabla `users`.

- **Pros:** Fuente única de verdad; no se necesita lógica de sincronización.
- **Contras:** Viola los límites de propiedad del servicio; los cambios de esquema requieren despliegues coordinados; el equipo del Auth Service prohíbe explícitamente el acceso directo a la base de datos desde servicios externos; introduce un punto único de fallo.

## Consecuencias

### Positivas

- **Desacoplamiento:** La aplicación no depende de la disponibilidad del Auth Service para cada interacción de usuario. El estado desactualizado se tolera hasta que llegue el evento.
- **Escalabilidad:** El procesamiento de eventos puede escalarse independientemente de la capacidad de manejo de solicitudes.
- **Auditabilidad:** La tabla `event_log` proporciona un registro completo y ordenado de cada cambio de estado consumido desde el Auth Service.

### Negativas

- **Consistencia Eventual:** Existe un retraso medible (sub-segundo a unos pocos segundos) entre la publicación de un evento y la actualización de la proyección local. La consistencia de lectura-después-de-escritura no está garantizada a través de los límites del servicio.
- **Complejidad de Infraestructura:** Requiere gestión de un espacio de nombres de Service Bus, tema, suscripción y cola de mensajes no procesables, además del ciclo de vida del host consumidor.
- **Sobrecarga Operativa:** Se deben definir procedimientos de monitoreo y reenvío de la cola de mensajes no procesables. Los cambios en el esquema de eventos requieren un despliegue coordinado entre publicador y consumidor.

### Mitigaciones

- **Idempotencia:** La protección de deduplicación mediante `eventId` garantiza que los eventos duplicados no corrompan el estado.
- **Verificación de Salud:** `UserStateSyncService` expone un endpoint de actividad que reporta el retraso entre el último evento procesado y la hora actual. El monitoreo alerta si el retraso supera los 60 segundos.
- **Proceso de Relleno:** Un script por lotes único reconcilia el conjunto completo de usuarios locales contra el Auth Service en el despliegue, luego cambia al modo basado en eventos.
- **Degradación Gradual:** Si el consumidor de eventos se retrasa o no está disponible, la aplicación continúa sirviendo solicitudes usando el estado almacenado localmente, aceptando que el estado puede estar desactualizado.

## Cumplimiento

Este ADR se alinea con los siguientes estándares organizacionales:

- **SEP-001 Límites de Servicio** -- la integración basada en eventos evita bases de datos compartidas y acoplamiento directo de API entre servicios.
- **SEP-007 Comunicación Asíncrona** -- toda sincronización de estado entre servicios utiliza mensajería intermediada.
- **SEP-012 Requisitos de Idempotencia** -- los consumidores de eventos deben manejar la entrega duplicada de forma segura.
