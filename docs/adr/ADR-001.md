# ADR-001: PostgreSQL sobre MongoDB para Perfiles de Usuario

**Estado:** Aceptado

**Fecha:** 2026-07-26

**Decisores:** Equipo de Arquitectura

---

## Contexto

El servicio de perfiles de usuario gestiona datos de usuario multiinquilino incluyendo detalles de cuenta, roles, permisos, registros de auditoría y relaciones organizacionales. El sistema requiere garantías de consistencia fuerte, integridad relacional entre entidades (usuarios, inquilinos, roles, trazados de auditoría) y seguridad a nivel de fila para imponer el aislamiento de inquilinos.

La base de datos debe soportar:

- **Consistencia fuerte** — sin ventanas de consistencia eventual para el estado del usuario o cambios de permisos.
- **Integridad relacional** — relaciones de clave foránea entre usuarios, inquilinos, roles y eventos de auditoría.
- **Multiinquilinato** — aislamiento estricto de datos de inquilinos en la capa de consulta sin filtrado a nivel de aplicación.
- **Registro de auditoría** — registro de eventos de solo agregado que referencia múltiples entidades relacionales.
- **Consultas ad-hoc** — consultas periódicas de cumplimiento y reportes a través de campos de usuario estructurados.

## Decisión

Usar **PostgreSQL 16** como almacén de datos principal para el servicio de perfiles de usuario.

Opciones clave de configuración:

- Desplegado via Azure Database for PostgreSQL Flexible Server (o servicio gestionado equivalente).
- Seguridad a Nivel de Fila (RLS) habilitada con una columna `tenant_id` en cada tabla multiinquilino.
- Réplicas de solo lectura para descargar consultas de auditoría/reportes.
- Agrupación de conexiones via PgBouncer para cargas de trabajo serverless/contenedorizadas.

## Alternativas Consideradas

### MongoDB

- **Pros:** Modelo de documento flexible, escalado horizontal listo para usar, bien entendido por el equipo.
- **Contras:** Sin soporte nativo para restricciones de clave foránea entre documentos; las uniones a nivel de aplicación aumentan la complejidad. El aislamiento multiinquilino requiere filtros de inquilino a nivel de aplicación o una estrategia de base de datos por inquilino (coste operativo). Las consultas de registros de auditoría que abarcan usuarios, inquilinos y roles son difíciles sin uniones reales. Los conjuntos de réplicas con consistencia eventual pueden servir estado de usuario desactualizado durante las comprobaciones de permisos.

### Azure Cosmos DB

- **Pros:** Completamente gestionado, distribución global, múltiples modelos de API.
- **Contras:** Sin integridad relacional ni uniones entre tipos de entidad sin código de aplicación o múltiples viajes de ida y vuelta. El aislamiento de inquilinos equivalente a RLS debe implementarse en middleware de aplicación. Los modos de consistencia transaccional son costosos (la consistencia fuerte limita el rendimiento) o débiles (obsolescencia acotada, sesión). Mayor coste por operación en comparación con PostgreSQL para los patrones de consulta necesarios.

### SQL Server

- **Pros:** Motor relacional maduro, consistencia fuerte, soporte de RLS.
- **Contras:** Mayor coste de licencia en infraestructura autogestionada; Azure SQL gestionado es competitivo en coste pero el equipo tiene experiencia operativa más profunda en PostgreSQL. Capacidades equivalentes con una historia de alta disponibilidad más compleja para los requisitos de escala del servicio.

## Consecuencias

### Positivas

- **Transacciones ACID** garantizan que las actualizaciones de perfil de usuario, asignaciones de roles y entradas de registro de auditoría se confirmen atómicamente.
- **Seguridad a Nivel de Fila** impone el aislamiento de inquilinos en la capa de base de datos — una aplicación mal configurada no puede filtrar datos entre inquilinos.
- **Integridad referencial** a través de claves foráneas evita registros de auditoría huérfanos y referencias de roles dangling.
- **Herramientas maduras** para respaldo, recuperación puntual, replicación lógica y monitoreo.
- **Columnas JSONB** permiten extensiones de esquema flexibles (metadatos de usuario, banderas de funcionalidad) dentro de filas relacionales cuando sea necesario.

### Negativas

- El escalado horizontal requiere fragmentación a nivel de aplicación o descarga a réplicas de solo lectura; PostgreSQL no se fragmenta automáticamente.
- Las migraciones de esquema requieren planificación cuidadosa (evitando bloqueos largos en tablas grandes de inquilinos).
- Sobrecarga de gestión de conexiones en entornos serverless (mitigado por PgBouncer).

### Neutrales

- El equipo debe mantener experiencia en ajuste de PostgreSQL (indexación, vacuum, planificación de consultas) en lugar de un conjunto de habilidades de almacén de documentos.
- La migración desde el almacén de datos existente (hipotético) requiere un esfuerzo de ETL; no se espera un período de doble escritura.

## Cumplimiento y Auditoría

La extensión `pgaudit` de PostgreSQL y los registros de transacciones satisfacen los requisitos de inmutabilidad para el almacenamiento de trazados de auditoría. Las políticas de RLS combinadas con roles de base de datos se asignan a controles de acceso con alcance de inquilino que se alinean con los requisitos de separación de datos de SOC 2 y GDPR.
