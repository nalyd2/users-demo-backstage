# ADR-001: PostgreSQL over MongoDB for User Profiles

**Status:** Accepted

**Date:** 2026-07-26

**Deciders:** Architecture Team

---

## Context

The user-profiles service manages multi-tenant user data including account details, roles, permissions, audit logs, and organizational relationships. The system requires strong consistency guarantees, relational integrity across entities (users, tenants, roles, audit trails), and row-level security to enforce tenant isolation.

The database must support:

- **Strong consistency** — no eventual consistency windows for user state or permission changes.
- **Relational integrity** — foreign-key relationships between users, tenants, roles, and audit events.
- **Multi-tenancy** — strict tenant data isolation at the query layer without application-level filtering.
- **Audit logging** — append-only event log referencing multiple relational entities.
- **Ad-hoc queries** — periodic compliance and reporting queries across structured user fields.

## Decision

Use **PostgreSQL 16** as the primary data store for the user-profiles service.

Key configuration choices:

- Deployed via Azure Database for PostgreSQL Flexible Server (or equivalent managed service).
- Row-Level Security (RLS) enabled with a `tenant_id` column on every multi-tenant table.
- Read replicas for audit/reporting query offloading.
- Connection pooling via PgBouncer for serverless/containerized workloads.

## Alternatives Considered

### MongoDB

- **Pros:** Flexible document model, horizontal scaling out of the box, well-understood by the team.
- **Cons:** No native support for cross-document foreign-key constraints; application-level joins increase complexity. Multi-tenant isolation requires application-level tenant filters or a database-per-tenant strategy (operational overhead). Audit-log queries spanning users, tenants, and roles are difficult without real joins. Eventually consistent replica sets can serve stale user state during permission checks.

### Azure Cosmos DB

- **Pros:** Fully managed, global distribution, multiple API models.
- **Cons:** No relational integrity or joins across entity types without application code or multiple round-trips. RLS-equivalent tenant isolation must be implemented in application middleware. Transactional consistency modes are either expensive (strong consistency limits throughput) or weak (bounded staleness, session). Higher per-operation cost relative to PostgreSQL for the query patterns needed.

### SQL Server

- **Pros:** Mature relational engine, strong consistency, RLS support.
- **Cons:** Higher licensing cost on self-managed infrastructure; managed Azure SQL is cost-competitive but the team has deeper PostgreSQL operational experience. Equivalent capabilities with a more complex high-availability story for the service's scale requirements.

## Consequences

### Positive

- **ACID transactions** guarantee that user-profile updates, role assignments, and audit-log entries are committed atomically.
- **Row-Level Security** enforces tenant isolation at the database layer — a misconfigured application cannot leak data across tenants.
- **Referential integrity** through foreign keys prevents orphaned audit records and dangling role references.
- **Mature tooling** for backup, point-in-time recovery, logical replication, and monitoring.
- **JSONB columns** allow flexible schema extensions (user metadata, feature flags) within relational rows when needed.

### Negative

- Horizontal scale-out requires application-level sharding or read-replica offloading; PostgreSQL does not auto-shard.
- Schema migrations require careful planning (avoiding long locks on large tenant tables).
- Connection management overhead in serverless environments (mitigated by PgBouncer).

### Neutral

- The team must maintain expertise in PostgreSQL tuning (indexing, vacuum, query planning) rather than a document-store skill set.
- Migration from the existing (hypothetical) data store requires an ETL effort; no dual-write period is expected.

## Compliance & Audit

PostgreSQL's `pgaudit` extension and transaction logs satisfy the immutability requirements for audit trail storage. RLS policies combined with database roles map to tenant-scoped access controls that align with SOC 2 and GDPR data-separation requirements.
