# ADR-002: JWT Validation at Gateway vs Service Level

- **Status:** Accepted
- **Date:** 2026-07-26
- **Deciders:** Platform Architecture Team

## Context

The system adopts a **zero-trust security model** in which no network boundary implies trust. Every request must be authenticated and authorized regardless of its origin or the hop it arrived through.

Our current architecture deploys an **API Gateway** (Kong / APISIX) as the single ingress point for all external traffic. Behind the gateway, multiple backend services process requests. A naive approach would rely exclusively on the gateway to validate JWTs and then pass an internal header (e.g., `X-User-Info`) to downstream services.

However, a zero-trust posture requires that a service must not implicitly trust any header received from an upstream proxy. An attacker who bypasses the gateway (e.g., via a misconfigured internal route, a compromised pod, or a direct cluster-network call) could forge the internal header and impersonate any user.

## Decision

**Validate the JWT at BOTH the API Gateway AND every backend service that receives the request.**

- The API Gateway performs the initial JWT validation, extracts claims, and forwards them to the backend service via a signed internal header or gRPC metadata.
- Each backend service independently re-validates the JWT (signature, expiry, issuer, audience) before processing the request.
- Services do not trust the gateway's forwarded headers alone; they always verify the original token.

## Alternatives Considered

### Gateway-Only Validation

Delegating all JWT validation to the API Gateway and having backend services trust the gateway's forwarded claims implicitly.

- **Pros:** Simpler service code, single point of validation policy, reduced latency per request.
- **Cons:** Violates zero-trust principles. A compromised or misconfigured gateway, or a request arriving via a non-gateway path, bypasses all auth. An attacker who reaches a service directly can forge the `X-User-Info` header.

### Service-Only Validation

Having each service validate its own JWT without gateway-level validation.

- **Pros:** Eliminates the gateway as a single point of failure for auth; services are fully self-reliant.
- **Cons:** Every unauthenticated request penetrates the full network path before being rejected. The gateway cannot reject invalid tokens early, wasting bandwidth and processing on malformed or expired tokens. Logging and rate-limiting of bad actors must be duplicated across every service.

### Shared Auth Sidecar (e.g., Istio mTLS + JWT filter)

Using a service-mesh sidecar to perform JWT validation at the pod level without modifying service code.

- **Pros:** Offloads validation from application code; policy is configured centrally via mesh CRDs.
- **Cons:** Still relies on the sidecar being present and correctly configured on every pod. A pod started without sidecar injection, or a sidecar with stale policy, silently trusts the request. This is a weaker form of gateway-only validation applied at a different layer.

## Consequences

- **Defense in depth:** Two independent validation layers prevent a single misconfiguration from exposing the system. The gateway provides perimeter defense; services provide perimiter-independent enforcement.
- **Negligible overhead:** JWT validation (RSA/ECDSA signature verification) is a single cryptographic operation per request, typically under 1 ms with cached public keys. Doubling it adds no measurable latency at the request volumes we serve.
- **Increased service complexity:** Each service must include a JWT validation library and refresh JWKS from the identity provider. This is a one-time implementation cost amortized across the service's lifetime.
- **Unified policy remains possible:** The gateway can still reject malformed or expired tokens early, so logging, rate-limiting, and bot-detection are centralized. Services only see requests that already passed the gateway check (plus direct internal calls that must also carry a valid JWT).
- **Key rotation discipline:** Because two layers consume the same JWKS endpoint, key rotation must be synchronized. The JWKS endpoint's cache TTL should be kept short (e.g., 5 minutes) so both layers converge quickly after a rotation event.
