# ADR-002: Validación de JWT a Nivel de Gateway vs Nivel de Servicio

- **Estado:** Aceptado
- **Fecha:** 2026-07-26
- **Decisores:** Equipo de Arquitectura de Plataforma

## Contexto

El sistema adopta un **modelo de seguridad de confianza cero** en el que ningún límite de red implica confianza. Cada solicitud debe ser autenticada y autorizada independientemente de su origen o del salto a través del cual llegó.

Nuestra arquitectura actual despliega un **API Gateway** (Kong / APISIX) como el único punto de ingreso para todo el tráfico externo. Detrás del gateway, múltiples servicios backend procesan solicitudes. Un enfoque ingenuo dependería exclusivamente del gateway para validar JWTs y luego pasaría un encabezado interno (ej., `X-User-Info`) a los servicios descendentes.

Sin embargo, una postura de confianza cero requiere que un servicio no confíe implícitamente en ningún encabezado recibido de un proxy ascendente. Un atacante que evade el gateway (ej., a través de una ruta interna mal configurada, un pod comprometido o una llamada directa a la red del clúster) podría falsificar el encabezado interno y suplantar a cualquier usuario.

## Decisión

**Validar el JWT en TANTO el API Gateway COMO en cada servicio backend que recibe la solicitud.**

- El API Gateway realiza la validación inicial del JWT, extrae los claims y los reenvía al servicio backend mediante un encabezado interno firmado o metadatos gRPC.
- Cada servicio backend re-valida independientemente el JWT (firma, expiración, emisor, audiencia) antes de procesar la solicitud.
- Los servicios no confían únicamente en los encabezados reenviados por el gateway; siempre verifican el token original.

## Alternativas Consideradas

### Validación Solo en Gateway

Delegar toda la validación de JWT al API Gateway y hacer que los servicios backend confíen implícitamente en los claims reenviados por el gateway.

- **Pros:** Código de servicio más simple, punto único de política de validación, latencia reducida por solicitud.
- **Contras:** Viola los principios de confianza cero. Un gateway comprometido o mal configurado, o una solicitud que llega por una ruta que no pasa por el gateway, evade toda la autenticación. Un atacante que alcanza un servicio directamente puede falsificar el encabezado `X-User-Info`.

### Validación Solo en Servicio

Hacer que cada servicio valide su propio JWT sin validación a nivel de gateway.

- **Pros:** Elimina el gateway como punto único de fallo para la autenticación; los servicios son completamente autosuficientes.
- **Contras:** Cada solicitud no autenticada penetra toda la ruta de red antes de ser rechazada. El gateway no puede rechazar tokens inválidos tempranamente, desperdiciando ancho de banda y procesamiento en tokens malformados o expirados. El registro y la limitación de tasa de actores maliciosos deben duplicarse en cada servicio.

### Sidecar de Autenticación Compartido (ej., Istio mTLS + filtro JWT)

Usar un sidecar de malla de servicios para realizar la validación de JWT a nivel de pod sin modificar el código del servicio.

- **Pros:** Descarga la validación del código de la aplicación; la política se configura centralmente mediante CRDs de la malla.
- **Contras:** Aún depende de que el sidecar esté presente y correctamente configurado en cada pod. Un pod iniciado sin inyección de sidecar, o un sidecar con política desactualizada, confía silenciosamente en la solicitud. Esta es una forma más débil de validación solo en gateway aplicada en una capa diferente.

## Consecuencias

- **Defensa en profundidad:** Dos capas de validación independientes evitan que una sola mala configuración exponga el sistema. El gateway proporciona defensa perimetral; los servicios proporcionan cumplimiento independiente del perímetro.
- **Sobrecarga insignificante:** La validación de JWT (verificación de firma RSA/ECDSA) es una única operación criptográfica por solicitud, típicamente por debajo de 1 ms con claves públicas en caché. Duplicarla no añade latencia medible en los volúmenes de solicitud que manejamos.
- **Mayor complejidad del servicio:** Cada servicio debe incluir una biblioteca de validación de JWT y actualizar JWKS desde el proveedor de identidad. Este es un costo de implementación único amortizado durante la vida útil del servicio.
- **Política unificada sigue siendo posible:** El gateway aún puede rechazar tokens malformados o expirados tempranamente, por lo que el registro, la limitación de tasa y la detección de bots están centralizados. Los servicios solo ven solicitudes que ya pasaron la verificación del gateway (más llamadas internas directas que también deben llevar un JWT válido).
- **Disciplina de rotación de claves:** Debido a que dos capas consumen el mismo endpoint JWKS, la rotación de claves debe estar sincronizada. El TTL de caché del endpoint JWKS debe mantenerse corto (ej., 5 minutos) para que ambas capas converjan rápidamente después de un evento de rotación.
